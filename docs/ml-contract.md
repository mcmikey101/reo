# контракт обмена backend ↔ ML

Описывает, как бэкенд вызывает ML-сервис, что передаёт и что получает, а также как бэкенд хранит результаты.

---

## 1. Общие правила

| Что | Правило |
|---|---|
| Транспорт | HTTP + JSON, кодировка UTF-8, `Content-Type: application/json` |
| Адрес | Внутри docker compose: `http://ml:8001`. Наружу сервис не публикуется |
| Аутентификация | Нет: сервис доступен только во внутренней сети compose |
| Версия контракта | Префикс `/v1`. |
| Даты | ISO 8601, `YYYY-MM-DD`. Неделя обозначается датой своего понедельника (ISO-неделя) |
| Числа | Индекс — число с одним знаком после запятой; вероятности и score — до 4 знаков |
| Идемпотентность | Один и тот же запрос при одной версии модели даёт одинаковый ответ. Повторять запросы безопасно |
| Повторы | При таймауте и ответах 5xx — до 3 повторов с паузой 1, 4 и 16 секунд. Ответы 4xx не повторяем |

### Формат ошибки

Любой ответ с кодом 4xx или 5xx имеет вид:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "reviews: ожидается от 1 до 256 элементов",
    "details": {"field": "reviews", "received": 300}
  }
}
```

| HTTP | `code` | Когда |
|---|---|---|
| 422 | `invalid_request` | Запрос не соответствует схеме: нет обязательного поля, неверный тип, превышен размер пачки |
| 503 | `model_not_ready` | Модель ещё загружается после старта сервиса. Повторить позже |
| 500 | `internal_error` | Непредвиденная ошибка сервиса |

Ошибка в одном отзыве **не** роняет всю пачку: такие случаи возвращаются в поле `status` конкретного результата (см. раздел 3).

## 2. Служебный эндпоинт

### `GET /v1/health`

Проверка готовности и текущие версии моделей. Бэкенд вызывает его при старте воркера и раз в несколько минут, чтобы заметить смену версии модели (см. раздел 6).

```json
{
  "status": "ok",
  "models": {
    "sentiment": "sent-0.1",
    "forecast": "fc-0.1"
  },
  "mock": false
}
```

`status`: `ok` — можно слать запросы; `loading` — модели загружаются, ответ приходит с кодом 503.

## 3. Тональность отзывов

### `POST /v1/sentiment`

Определяет тональность пачки отзывов. Вызывается из фонового воркера бэкенда, не из пользовательского запроса.

**Запрос**

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `reviews` | массив | да | От 1 до 256 отзывов |
| `reviews[].id` | string | да | Идентификатор отзыва в БД бэкенда. Возвращается без изменений |
| `reviews[].text` | string \| null | да | Текст отзыва, до 10 000 символов. |
| `reviews[].rating` | number \| null | да | Оценка 1–5 с площадки или из CSV; `null`, если оценки нет |

```json
{
  "reviews": [
    {"id": "r1", "text": "Кофе отличный, но заказ ждали 40 минут", "rating": 3},
    {"id": "r2", "text": null, "rating": 5},
    {"id": "r3", "text": "", "rating": null}
  ]
}
```

**Ответ** — `200 OK`, результаты в том же порядке, что и в запросе.

| Поле | Тип | Описание |
|---|---|---|
| `model_version` | string | Версия модели, которой посчитана пачка. Сохраняется вместе с результатом |
| `results[].id` | string | Идентификатор из запроса |
| `results[].status` | string | `ok` или `skipped` |
| `results[].reason` | string \| null | Причина пропуска, например `no_text_no_rating` |
| `results[].method` | string \| null | `model` — по тексту; `rating` — по звёздам, когда текста нет |
| `results[].label` | string \| null | `positive`, `neutral` или `negative` |
| `results[].probs` | object \| null | Вероятности классов `pos`, `neu`, `neg`; в сумме 1 |
| `results[].score` | number \| null | `probs.pos − probs.neg`, от −1 до 1. Основа индекса |

```json
{
  "model_version": "sent-0.1",
  "results": [
    {"id": "r1", "status": "ok", "reason": null, "method": "model",
     "label": "neutral", "probs": {"pos": 0.30, "neu": 0.45, "neg": 0.25}, "score": 0.05},
    {"id": "r2", "status": "ok", "reason": null, "method": "rating",
     "label": "positive", "probs": {"pos": 1.0, "neu": 0.0, "neg": 0.0}, "score": 1.0},
    {"id": "r3", "status": "skipped", "reason": "no_text_no_rating", "method": null,
     "label": null, "probs": null, "score": null}
  ]
}
```

**Правила**

- Есть непустой текст → тональность по тексту (`method: model`). Оценка в MVP на результат не влияет. **[к обсуждению]** Смешивать ли текст и звёзды.
- Текста нет, но есть оценка → тональность по звёздам (`method: rating`): 1–2 → `negative`, 3 → `neutral`, 4–5 → `positive`; вероятности 1/0/0, score −1, 0 или 1.
- Нет ни текста, ни оценки → `status: skipped`. Такой отзыв не участвует в индексе, но учитывается в числе отзывов на дашборде.
- Ориентир по скорости: пачка из 256 отзывов на CPU — несколько секунд. Точные цифры будут в отчёте о качестве модели к 25.11.

## 4. Индекс удовлетворённости и агрегаты

Индекс считает **бэкенд** по формуле ниже, из сохранённых агрегатов. ML-сервис для каждого показателя дашборда не вызывается. Формула принадлежит ML: при её изменении ML обновляет этот раздел и тестовые примеры.

### Формула

```
score(отзыв)   = p_pos − p_neg                          ∈ [−1; 1]
индекс(выборка) = 50 × (1 + Σ score / n)                ∈ [0; 100]
```

где `n` — число отзывов выборки со `status: ok`. При `n = 0` индекс равен `null`, на дашборде показываем «Нет данных».

При жёстких метках формула совпадает с `(позитив + 0,5 × нейтрально) / n × 100`: так её можно объяснить пользователю в подсказке.

**[к обсуждению]** Сглаживание для точек с малым числом отзывов (например, `n < 10`): `50 × (1 + (Σ score + k × m) / (n + k))`, где `m` — средний score по организации, `k = 10`. Предлагаю применять только в таблице точек, чтобы точка с одним отзывом не оказывалась первой или последней.

### Агрегаты, которые хранит бэкенд

Бэкенд хранит дневные суммы по каждой комбинации «точка × источник × день». Индекс любой выборки и любого периода получается сложением сумм — без повторного запуска модели и без ошибки «среднее от средних».

| Поле | Тип | Описание |
|---|---|---|
| `organization_id`, `point_id`, `source_id` | id | Ключ |
| `date` | date | День публикации отзыва |
| `n_total` | int | Все отзывы за день, включая пропущенные |
| `n` | int | Отзывы со `status: ok` |
| `n_pos`, `n_neu`, `n_neg` | int | Отзывы по меткам — для KPI «доля позитива / негатива» и распределения тональности |
| `score_sum` | float | Сумма score — для индекса |

Агрегаты пересчитываются из таблицы результатов (раздел 6) после каждой обработанной пачки. Недели собираются из дней по ISO-неделям.

**[к обсуждению]** Часовой пояс для даты отзыва. Предложение для MVP — один фиксированный пояс (Europe/Moscow), пояс точки — после MVP.

### Тестовые примеры

Бэкенд проверяет свою реализацию на этих примерах; ML держит такие же тесты у себя.

| № | Отзывы выборки (score) | n | Σ score | Индекс |
|---|---|---|---|---|
| 1 | 1, 1, 0, −1 | 4 | 1 | 62.5 |
| 2 | −1, −1, −1 | 3 | −3 | 0.0 |
| 3 | 0.6, −0.5 | 2 | 0.1 | 52.5 |
| 4 | нет отзывов | 0 | 0 | `null` |

## 5. Тренд, сезонность и прогноз (E8 · ML-3)

### `POST /v1/forecast`

Строит тренд, сезонность и прогноз индекса для ряда текущей выборки. Вызывается при открытии дашборда или смене выборки. Ответ бэкенд кэширует по ключу «параметры выборки + время последнего обновления агрегатов» и повторно не запрашивает, пока данные не изменились.

**Запрос**

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `granularity` | string | да | `week` (по умолчанию для MVP) или `day` |
| `horizon` | int | нет | На сколько периодов прогнозировать, 1–12, по умолчанию 4 |
| `interval` | number | нет | Уровень доверительного интервала, `0.8` или `0.95`, по умолчанию `0.8` |
| `series` | массив | да | Ряд по возрастанию дат, **без пропусков**: период без отзывов передаётся с `n = 0` |
| `series[].period` | date | да | Начало периода (для недели — понедельник) |
| `series[].n` | int | да | Число отзывов со `status: ok` за период |
| `series[].score_sum` | number | да | Сумма score за период |

Индекс по периоду ML считает сам по формуле из раздела 4 и учитывает `n` как вес: период с 2 отзывами влияет на модель меньше, чем период с 200.

```json
{
  "granularity": "week",
  "horizon": 4,
  "interval": 0.8,
  "series": [
    {"period": "2026-09-07", "n": 23, "score_sum": 9.4},
    {"period": "2026-09-14", "n": 0,  "score_sum": 0.0},
    {"period": "2026-09-21", "n": 31, "score_sum": 14.2}
  ]
}
```

**Ответ** — `200 OK`. Каждая компонента сообщает, доступна ли она, чтобы фронт показывал то, что есть, а остальное помечал «Недостаточно данных».

| Поле | Тип | Описание |
|---|---|---|
| `model_version` | string | Версия модуля прогноза |
| `status` | string | `ok` — всё доступно; `partial` — часть компонент недоступна; `insufficient_data` — недоступны тренд и прогноз |
| `history[]` | массив | По одному элементу на каждый период запроса |
| `history[].period` | date | Период |
| `history[].n` | int | Число отзывов |
| `history[].index` | number \| null | Индекс периода; `null` при `n = 0` |
| `history[].trend` | number \| null | Значение тренда; `null`, если тренд недоступен |
| `history[].seasonal` | number \| null | Сезонная поправка в пунктах индекса; `null`, если сезонность недоступна |
| `trend.available` | bool | Доступен ли тренд |
| `trend.direction` | string \| null | `up`, `down` или `flat` — для подписи «Индекс растёт» |
| `trend.change_per_period` | number \| null | Изменение тренда за период, в пунктах индекса |
| `seasonality.available` | bool | Найдена ли сезонность |
| `seasonality.period` | int \| null | Длина сезона в периодах: 52 для недель, 7 для дней |
| `forecast.available` | bool | Доступен ли прогноз |
| `forecast.model` | string \| null | Описание модели, например `ARIMA(1,1,0)` — для отладки, пользователю не показываем |
| `forecast.points[]` | массив | `period`, `index`, `lo`, `hi`. Границы интервала обрезаны до [0; 100] |
| `*.reason` | string \| null | Причина недоступности компоненты (коды ниже) |

```json
{
  "model_version": "fc-0.1",
  "status": "partial",
  "history": [
    {"period": "2026-09-07", "n": 23, "index": 70.4, "trend": 68.9, "seasonal": null},
    {"period": "2026-09-14", "n": 0,  "index": null, "trend": 69.3, "seasonal": null},
    {"period": "2026-09-21", "n": 31, "index": 72.9, "trend": 69.7, "seasonal": null}
  ],
  "trend": {"available": true, "direction": "up", "change_per_period": 0.4, "reason": null},
  "seasonality": {"available": false, "period": null, "reason": "history_too_short"},
  "forecast": {
    "available": true,
    "model": "ARIMA(1,1,0)",
    "points": [
      {"period": "2026-11-09", "index": 71.2, "lo": 64.0, "hi": 78.3}
    ],
    "reason": null
  }
}
```

**Пороги доступности** (стартовые значения, уточню на бэктесте в спринте 4)

| Компонента | Недели | Дни | Код при нехватке |
|---|---|---|---|
| Тренд | от 8 периодов с `n > 0` | от 28 | `history_too_short` |
| Прогноз | от 12 периодов с `n > 0` | от 42 | `history_too_short` |
| Сезонность | от 104 периодов (2 года) | от 56 (8 недель, сезон по дням недели) | `history_too_short` |
| Любая | доля пустых периодов больше 50% | то же | `too_sparse` |

Даже при `status: insufficient_data` поле `history` с индексом по периодам заполнено: главный график строится всегда, без линий тренда и прогноза.

## 6. Конвейер обработки на стороне бэкенда

1. Новый отзыв после сбора или импорта CSV и удаления дублей получает статус анализа `pending`.
2. Воркер забирает до 256 отзывов со статусом `pending`, переводит их в `processing` и вызывает `/v1/sentiment`.
3. Результаты сохраняются в таблицу результатов (ниже), статус меняется на `done` или `skipped`, затем пересчитываются дневные агрегаты затронутых дней.
4. Если запрос не удался после 3 повторов, отзывы пачки получают статус `error` и время следующей попытки. Ошибка одной пачки не останавливает остальные.
5. Статус источника на M2 («идёт сбор / готово / ошибка») учитывает и анализ: источник «готов», когда у его отзывов не осталось `pending` и `processing`.

**Таблица результатов тональности**

| Поле | Тип | Описание |
|---|---|---|
| `review_id` | id, PK | Ссылка на отзыв |
| `status` | enum | `pending`, `processing`, `done`, `skipped`, `error` |
| `method` | enum \| null | `model` или `rating` |
| `label` | enum \| null | `positive`, `neutral`, `negative` — для карточки отзыва (E5) и фильтров |
| `p_pos`, `p_neu`, `p_neg` | float \| null | Вероятности |
| `score` | float \| null | Для индекса |
| `model_version` | string \| null | Чем посчитано |
| `analyzed_at` | timestamp \| null | Когда посчитано |

**Смена версии модели.** Если `/v1/health` вернул версию тональности, отличную от сохранённой у отзывов, бэкенд в фоне с низким приоритетом переводит такие отзывы в `pending` и пересчитывает их. Пока идёт пересчёт, дашборд работает на старых результатах. **[к обсуждению]** Делать ли это автоматически или по команде администратора.
